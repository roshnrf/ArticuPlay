## 2026-07-26 — Fine-tuned model integrated into production; CPU latency tight, but not from beam_size
Integrated the 491-vocab fine-tuned model into production `ASRService`: merged LoRA into base weights (`merge_and_unload()`), converted to CTranslate2 format (`ct2-transformers-converter` — needed an isolated venv with newer `transformers`, since ctranslate2 4.8.1's converter uses a `transformers` API our training venv's 4.46.3 doesn't have), copied to `backend/ml_models/storyweaver_whisper_v1/`, added `WHISPER_MODEL_PATH` setting. Also removed `initial_prompt` target-word biasing per the ablation decision (see false-accept/reject entry) and bumped `beam_size` 1→5. Verified end-to-end via the live `/session/transcribe` endpoint — real fix confirmed: 'cone' (real UXSSD sample, genuinely correct pronunciation) now transcribes correctly, previously failed under base+biased ('Cologne').
Found the endpoint's real-world latency (~3.0-3.5s) is meaningfully higher than the GPU research number (899ms) — expected, since prod deliberately runs CPU (`device="cpu"`, Week 1 cost decision). Tested whether `beam_size=5` was the cause by sweeping 1/3/5 directly against `WhisperModel.transcribe()` — it wasn't: beam=1 (2340ms), beam=3 (1957ms), beam=5 (1987ms) are all roughly equal on CPU. The real gap between this (~2s) and the endpoint's ~3.2s is webm decoding + FastAPI overhead, not beam search. Kept beam_size=5 (free accuracy, no latency cost). Net: CPU latency is at/near the 3s budget with no headroom — real constraint, not fixed further (would need webm-decode optimization or GPU hosting). Flag before any live pilot with real users.

## 2026-07-26 — Bias ablation: real tradeoff, not a clean fix (28%→15% false-accept, but 32%→44% false-reject)
Tested removing `prompt_ids` target-word bias on the fine-tuned LoRA model, same 200 UXSSD real-disordered-speech samples (`error_type_nobias.py`). Result: false-accept 28%→15% (real improvement, the clinically dangerous direction), false-reject 32%→44% (worse, but less harmful — kid retries something already correct instead of a wrong pattern going unflagged). Overall raw accuracy barely moves (70% vs 70.5%) — it's a redistribution of error type, not a net win. 15% false-accept remains even unbiased ('pram', 'zebra', 'frog', 'bread' with real bad consonants still pass) — confirms the deeper limit is ASR-transcription-text scoring itself, which can't catch phone errors subtle enough that the word still sounds "right." Real fix is routing scoring through the already-built 67.9% phone classifier instead of `compare_ipa`-on-transcript.
**IMPORTANT CAVEAT before acting on this**: this ablation was run on the fine-tuned LoRA model. Production `ASRService` (`backend/app/services/asr_service.py`) still runs the untrained base faster-whisper model — LoRA integration into the product was never done (separate pending decision). Week 1's own finding was that removing `initial_prompt` on the *base* model drops single-word accuracy 92%→42%. Do NOT flip prod's bias off on the base model — that finding doesn't transfer, and would likely reintroduce the Week 1 regression for zero benefit. Unbiased-by-default only makes sense bundled with the fine-tuned-model integration. Decision pending: cautious (update research default only, hold prod change until integration) vs bundle both changes together now. Asked Rosh, awaiting answer.

## 2026-07-26 — CRITICAL: false-accept 28%, false-reject 32% on real disordered child speech — target-word prompt biasing masks real errors
All prior "95-96% generalization" numbers were tested on synthetic TTS audio, which always pronounces the word correctly — so they only ever tested word-recognition, never error-detection, which is the app's actual clinical job. Ran `error_type_analysis.py` against real UXSSD child speech (clinician-labeled primary_score, 100 genuinely-correct + 100 genuinely-disordered segments, real audio not synthetic). Result: **false-accept 28%, false-reject 32%**. Root cause visible in the false-accept examples: 'tiger' with a real bad /g/, 'zebra'/'frog'/'string' with a real bad /r/ — all transcribed back as the perfectly-spelled target word (score 1.00) despite the audio containing a genuine articulation error. This traces to the `prompt_ids`/target-word biasing added early in the project (see the 2026-07-26 Whisper-needs-target-word-hint entry) — it fixes short isolated-word transcription accuracy but also biases the decoder toward outputting the target spelling almost regardless of subtle phonetic deviation, directly undermining error detection. This is a real architectural tension (word-recognition accuracy vs error-sensitivity), not a tunable bug — needs a design decision: weaker/no prompt biasing + accept worse raw word-recognition, or a second-pass phone-level classifier (the already-built 67.9% LoRA phone classifier, currently unintegrated) as the actual error signal instead of relying on transcription text. Top-priority open item.

## 2026-07-26 — Latency: mean 899ms, p95 2319ms, max 2464ms (budget 3000ms) — and it correlates with the loop failure
Measured real GPU inference time (model.generate only, beam=5, not incl. model load/network/FastAPI overhead) across 22 words spanning all 5 levels — `measure_latency.py`. First attempt had an audio-index bug (level5 slots miscounted, grabbed level4 audio for the last 2 rows) — caught it because the printed transcript didn't match the claimed target word, re-verified by fixing indices and rerunning rather than accepting the first numbers. Real result: mean 899ms, p95 2319ms, max 2464ms — passes the 3s budget but with limited margin on the slow tail. Notable: the 5 slowest cases (moth 2208ms, badger 2259ms, wonderful 2319ms, fabulous 2242ms, athletic 2464ms) cluster right at the ceiling, and 'moth' — the one genuine transcription failure (repetition-loop garbage) in this batch — is among them. Suggests beam search burning through `max_new_tokens=48` without finding an early EOS correlates with bad output, not just slowness. Not confirmed causal, but a real pattern worth watching — a token-budget or repetition-penalty tweak might fix both the tail latency and the loop failures at once.

## 2026-07-26 — Never grep/sed a file containing secrets with a "masking" regex
Tried to verify `.env` contents by grepping the DATABASE_URL line and using a sed pattern to mask the password before printing. The masking regex was anchored to an expected prefix/structure; when the actual line didn't match that structure (wrong driver prefix, stray brackets), the mask silently failed to apply and the raw password printed in full — twice, with two different regex attempts. Both times required the user to reset their DB password.
**Fix:** never construct a "safe preview" of a secret value via string manipulation — the failure mode is silent and prints the raw secret. Instead, only ever ask boolean structural questions (`grep -c` for an expected prefix/suffix, checking length, checking for a literal placeholder string) and only print the count/true-false, never any substring derived from the value itself.

## 2026-07-26 — Whisper needs the known target word as a hint on short isolated-word audio
Discovered while testing the TTS→transcribe loop: `faster-whisper` (base model) got only 5/12 (42%) of common drill words right when transcribing isolated single-word clips with no sentence context — it defaults to whatever sounds like a plausible short utterance ("cat"→"yeah", "dog"→"duh!"). This directly threatens Level 1 (single-syllable words), the app's easiest/first tier.
**Fix:** always pass the drill's target word as Whisper's `initial_prompt` — legitimate, not "cheating," since the app already knows the word (it just spoke it via TTS). Took accuracy to ~92% in testing. Also found the default `temperature` fallback ladder makes results non-deterministic (same input, different output ~1 in 5 calls) — pin `temperature=0.0` for reproducibility. General takeaway: don't assume a generic ASR/NLP tool's out-of-the-box behavior transfers to a narrow, constrained-vocabulary use case — test the actual task shape (short isolated words, not sentences) before trusting published benchmarks.

## 2026-07-25 — New GPU architectures need current framework versions, `cuda.is_available()` isn't enough
Pinned `torch==2.5.1` for the phone-classifier research venv. `torch.cuda.is_available()` returned `True` — looked fine — but a real op (`torch.randn(3,3).cuda() @ ...`) printed a warning that `sm_120` (RTX 5070 Ti's Blackwell architecture) isn't in that build's supported compute capability list (`sm_50` through `sm_90` only). `is_available()` only checks driver/CUDA visibility, not whether the installed build has kernels for this specific GPU generation. Fix: upgraded to `torch==2.13.0` (`+cu130` wheel), real matmul on GPU confirmed working after. Lesson: always test an actual op on new/bleeding-edge hardware, not just the availability check — especially right after a new GPU generation launches, since framework kernel support lags behind driver support.

## 2026-07-25 — Full fine-tune on a narrow dataset overfits to that dataset's specific world, not "child speech" in general
Fine-tuned Whisper-small (full fine-tune, all weights, 3 epochs) on UXTD — WER improved 1.695→0.205 on UXTD's own held-out test set, looked like a big win. Tested it against StoryWeaver's actual product vocabulary (cat/rabbit/spoon/etc, real words, different from UXTD's specific prompts) and it scored *worse* than plain base Whisper (4/8 vs 8/8), including two outright hallucinated outputs matching what looks like a literal UXTD session-label string leaked into training data. Root cause: full fine-tuning on a comparatively tiny dataset (3640 examples) relative to Whisper's original pretraining scale (~680k hours) let the model overwrite broad general knowledge in favor of narrow UXTD-specific memorization — classic overfitting + catastrophic forgetting. The *same session* correctly used LoRA (not full fine-tune) for the phone classifier specifically to avoid this risk — inconsistent reasoning applied to the transcriber ("more data available, so full fine-tune is fine") that didn't hold up. Lesson: default to parameter-efficient fine-tuning (LoRA) for domain adaptation on anything smaller than pretraining-scale data, and always validate against the *actual deployment* data distribution before trusting a held-out-same-domain metric, not just after something looks suspicious.

## 2026-07-25 — The real root cause wasn't full-fine-tune-vs-LoRA, it was contaminated training data
After LoRA also reproduced the same "double-articulation pre-test no-context"-style hallucinations as the full fine-tune, checked the actual training text files directly instead of assuming LoRA would fix it. Found: ~37% (1688-1856 of 4609) of UXTD's `.txt` "prompt" files aren't speech content at all — they're session-administration labels (`"<phonetic-feature> teaching|pre-test|post-test <no-context|dV|aCa>"`, 36 unique templates) that got included as if they were normal transcription targets. Both full fine-tune and LoRA correctly learned to reproduce this leaked text on unfamiliar audio, since it was genuinely present in their training labels — this was never really a capacity/overfitting question, it was a data-cleaning question. Lesson: when a fine-tuned model hallucinates suspiciously specific, repeated, non-natural-language text, check the raw training labels for exactly that string before assuming it's a training-method problem — grep the data before reaching for a different algorithm.

## 2026-07-25 — A small test sample gave a falsely optimistic picture; the real fix needed a complete audit, not another regex guess
First contamination fix (regex on "teaching|pre-test|post-test") looked like it worked on a small 8-word spot check (6/8 correct, no more garbage). Testing at real scale (all 250 real product words, per the user's explicit push to test properly instead of trusting the small sample) revealed it was still badly broken: base Whisper 98.8%, "fixed" model only 41.6% — the regex missed a whole second contamination category (standalone phonetic-jargon words like "linguolabial", "velar", "alveolar", "cardinal-1", "swallow" — no compound marker for a regex to catch). Root-fixed properly this time by auditing literally all unique prompt values in the corpus (only 100 total — small enough to review by hand) and building an exact-match denylist instead of pattern-guessing. Turned out 66% of the corpus (3042/4609) was contaminated, not the ~37% first estimated. Lesson: a small before/after sample can look convincing while completely missing a problem that only shows up at scale — when the full unique-value space is small enough to enumerate, audit all of it rather than spot-checking and extrapolating.

## 2026-07-25 — How the accuracy improvement was actually achieved (methodology, not just the numbers)
Went from a badly broken model (41.6% on real product words) to a real, honest improvement (73.6%) through two distinct techniques, in this order:

**1. Diagnose from evidence, not assumption, before touching training code again.** Each time accuracy was bad, looked at the *actual failure examples* instead of just the aggregate number: garbled leaked text → grep the training data for that exact string (found contamination); a category-specific collapse (Level 5 only) → checked audio duration first (ruled it out, median 5.4s wasn't short) → checked linguistic content next (found the real cause: training data was all word-lists/nonsense-syllables, zero grammatical sentences). The specific failure pattern told us exactly what to check — never guessed at a fix without a diagnosis backed by real evidence first.

**2. Fix the data, not (only) the training method.** The instinct was to blame the training approach (full fine-tune vs LoRA) — turned out to be a red herring; the real problem both times was the *data*: contaminated labels first, then missing sentence-structure content second. Once each was correctly diagnosed, the fix was small and targeted — an exact-match denylist (contamination) and 100 synthetic sentence examples generated from the app's own real content (missing structure) — not a bigger model, not more epochs, not a different algorithm.

**3. Validate at the scale you'll actually deploy at, every time.** A small 8-word sample said the first fix worked (6/8). Testing all 250 real product words revealed it was still 41.6% broken. The full-scale test is what caught it — small samples can look convincing while hiding a real problem that only shows up at scale.

General pattern for next time: bad model output → find concrete failure examples → diagnose the specific mechanism (don't guess) → fix the smallest specific thing that addresses that mechanism → re-validate at full/real scale, not a spot check.

## 2026-07-25 — A "premature stopping" symptom was a decoding-strategy problem, not a training problem
Augmented model produced empty/truncated outputs ("ball"→"", "elephant"→"ele", "He climbs the tall tree."→"He") — looked like premature end-of-sequence prediction. Tested `min_new_tokens` (forces the model to not stop early) first, since that directly targets the EOS theory — zero effect, outputs identical. That result, not a guess, is what ruled the theory out. Tried beam search (`num_beams=5, length_penalty=1.5`) instead — different mechanism, explores multiple candidate continuations rather than committing to the single greedy path — and it fixed most of the truncated cases immediately, then verified at full 250-word scale: 73.6%→85.2% for zero retraining cost. Lesson: a "the model won't finish generating" symptom isn't automatically a training/data problem — try changing the decoding strategy first, it's free (no retrain needed) and can be tested in minutes, before assuming you need to fix the model itself.

## 2026-07-25 — The winning fix was training on the actual deployment vocabulary, not more UXTD data
After beam search closed most of the gap (73.6%→85.2%), the remaining weakness was diagnosed as vocabulary mismatch — UXTD's word lists are different words than StoryWeaver's actual 250-word product bank, so the model had never seen most of the real target vocabulary during training. Fix: synthesized all 250 real product words via the actual `/session/tts` endpoint and added them to training (1243 UXTD + 250 synthetic = 1493). Result: model went from behind base Whisper to genuinely beating it under the real phoneme-scoring method (94.8% vs 87.6%). Lesson: when a fine-tuned model underperforms on your specific real-world vocabulary, check whether it ever saw that vocabulary at all during training before assuming a deeper architectural or capacity problem — sometimes the fix is just "show it your actual words."
